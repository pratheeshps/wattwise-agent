# Sprint 6 — Production Readiness Foundation

**Status:** Infrastructure foundation added; application cutover and deployment verification remain pending.  
**Branch:** `feature/analytics-first-dashboard`  
**Principles:** user-owned data, tenant-scoped reads/writes, private PDF objects, no secrets in source control.

## Decisions implemented

- PostgreSQL is the production metadata store, accessed through Prisma ORM 7 and the PostgreSQL driver adapter.
- Better Auth provides email/password authentication. Email verification is required and passwords must be at least 12 characters.
- Every bill row is owned by a Better Auth user. Database uniqueness and indexes are scoped by user.
- PDF files use a private S3-compatible object store. The adapter supports AWS S3 and S3-compatible endpoints such as Cloudflare R2.
- Object keys are generated by the server and are never exposed in public bill API projections.
- Local JSON/PDF persistence remains the existing development/legacy path until the API cutover and migration have been completed.

## Added foundation

- `prisma/schema.prisma`: Better Auth models and user-owned Bill model.
- `prisma.config.js`: Prisma 7 configuration using `DATABASE_URL`.
- `src/lib/prisma.js`: singleton Prisma client with PostgreSQL driver adapter.
- `src/lib/auth.js`, `src/lib/auth-client.js`: Better Auth server/client configuration.
- `src/app/api/auth/[...all]/route.js`: Better Auth route handler.
- `src/lib/requireSession.js`: server-side session guard helper.
- `src/services/postgresBillStore.js`: user-scoped PostgreSQL bill CRUD.
- `src/services/objectStorage.js`: private S3-compatible PDF put/delete and short-lived download URL helpers.

## Required environment

See `.env.example`. Production must set database credentials, a high-entropy Better Auth secret, the canonical app URL, trusted origins, and private object-store credentials. Do not expose S3 credentials with a `NEXT_PUBLIC_` prefix.

## Migration and rollout

1. Provision PostgreSQL and a private S3/R2 bucket.
2. Set environment variables in the hosting provider.
3. Run `npm run db:generate` and `npm run db:migrate:deploy` during controlled deployment.
4. Create/verify the first account after configuring a transactional email sender. Email verification is intentionally required; sign-up is not considered production-ready until email delivery is configured and tested.
5. Integrate `getRequiredSession()` into every bill, preview and analysis API route. All queries must use the authenticated user ID; never accept userId from request bodies.
6. Switch bill routes and the analysis tool from the local JSON store to the user-scoped PostgreSQL store. Upload the PDF object before creating the bill row; if the DB write fails, delete the newly uploaded object. For deletion, delete only the object key belonging to the authenticated user's row.
7. Add an explicit one-time migration command for legacy `data/bills.json` and `data/uploads/` after the destination user account is known. Verify record counts and SHA-256 values before deleting any local source data.
8. Run regression, production build, smoke, authentication, tenant-isolation, upload rollback, duplicate upload and object deletion tests.
9. Deploy to a Node.js hosting target with persistent PostgreSQL and private object storage. Do not rely on a serverless filesystem for bill persistence.

## Security and operational acceptance

- Unauthenticated requests to bill, preview, delete and analysis APIs must return 401.
- A user must never read, delete, or analyze another user's bill by guessing an ID.
- Database uniqueness is `(userId, sha256)`, not global across unrelated users.
- Bucket access is private; only short-lived signed downloads are permitted.
- Enforce the existing 10 MB PDF limit and PDF signature check before object upload.
- Do not log consumer numbers, PDF bytes, signed URLs, secrets, or storage credentials.
- Backups, restore drills, rate limits, email delivery, account recovery and monitoring are deployment gates.

## Important completion boundary

This commit adds the database/auth/object-storage foundation but deliberately does not switch the live dashboard API away from local JSON storage yet. The current UI still calls the legacy bill endpoints, and those endpoints must not be exposed publicly until session enforcement and storage cutover are complete. Sprint 6 is therefore not deployment-complete. The next implementation increment must wire session checks and PostgreSQL/object storage through all existing API and agent paths, then add sign-in/sign-up UI and the legacy-data migration tool.
